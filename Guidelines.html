How to Answer the Application Specification Builder

This guide goes through all 10 questions in the Application Specification Builder. For each one it covers what the question is really asking, what a complete answer contains, how long it should be, and the mistakes that lead to a weak specs.md. It's written for a workflow where an AI coding assistant generates the full-stack app from the spec, and you hand-code the AI/LLM integration yourself.

Before you start: how the builder uses your answers

  • Your answers are pasted straight into Markdown. Each field becomes a section under ## 1. … ## 10., so you can use Markdown inside the text boxes: - bullets, 1. numbered lists, **bold**, `code`, and simple tables. Don't add # or ## headings of your own. Use **Bold labels:** or #### for sub-headings so the document hierarchy stays intact.
  • The builder already adds boilerplate. Every spec automatically gets "build end-to-end, no mockups, never hardcode secrets, write a README, .env.example, tests, definition of done". Don't repeat any of that. Use your words on things that are specific to this project.
  • The reader is an AI coding assistant. It takes every sentence literally and fills any gap with a guess. Wherever a guess would be wrong, write the decision down: the exact field names, numbers, messages, and states.
  • Every field is required. If something doesn't apply, write a short reason ("No authentication — single-user local demo") rather than leaving it blank, or the spec will say "Not specified yet."
The manual-AI boundary. You plan to write the AI agent integration by hand, so the spec has to tell the assistant exactly where to stop. Describe the AI module's interface (function names, inputs, return schemas, behaviour when not configured) and tell it to generate stubs plus a deterministic fallback instead of real LLM calls. That boundary should show up in Q4, Q6, Q8, Q9 and Q10. Each question below has a "Manual-AI note" saying what to put there.

General writing rules

  • Specific beats generic. "Flag any subscription whose amount rises by more than 10% versus the previous charge" is a spec. "Detect price hikes" is a wish.
  • Use the same name for a thing everywhere. If it's Transaction.raw_line in Q5, don't call it "source text" in Q7.
  • Give every feature and test an ID (F1, L3, AC4). The assistant can cross-reference them, and so can you when you review the generated code.
  • Write numbers, not adjectives: limits (12 MB), caps (6 iterations), thresholds (10%), and example values ($37.69 → $49.00).
  • Only state a technology if you've decided on it. If you haven't, describe the need ("a chart of monthly spend") and let the assistant choose.
  • Put must-haves first and label nice-to-haves clearly, so the assistant doesn't over-build.

1

Project name and overview

Two fields: "Project name" (one line) and "Short overview" (a paragraph).

Length: name 2–5 words · overview 80–150 wordsFormat: prose

What it's really asking

The elevator pitch. This is the first thing the assistant reads, and it frames every later decision: what kind of app this is, its shape (web app, CLI, API), and its scope (demo or production).

A good answer includes

  • Name: the product or repo name, plus a UI brand name if it's different (e.g. "Finance Intelligence Agent", branded "Finwise" in the UI).
  • What it is, in one sentence: type of app plus the core value.
  • The main parts or layers (e.g. "an extraction layer and an agent layer").
  • Primary user journey in one line: input → processing → output.
  • Scope and maturity: demo, workshop, MVP or production. This sets the level of rigour the assistant aims for.
  • Stack in a phrase, if you've decided (e.g. "React + FastAPI").
Weak
An AI app for finance that helps users with money.
Strong
A full-stack teaching demo (React + FastAPI) where users paste or upload transactions, an AI extracts them into validated records, a dashboard summarises spending, and a bounded agent audits subscriptions for silent price hikes, then drafts a dispute message that needs human approval. It never sends anything.

Common mistakes

  • Listing features here. Save them for Q4.
  • Not saying whether it's a demo or production. The assistant will then guess auth, databases and so on.
2

Problem statement

The pain point, its impact, and the outcome you want.

Length: 100–200 words or 4–8 bulletsFormat: Pain → Impact → Outcome

What it's really asking

Why the app exists. The assistant uses this to break ties. When a requirement is ambiguous, it picks whichever reading best solves the stated problem.

A good answer includes

  • Current pain: what users do today and why it fails (manual, slow, error-prone, invisible).
  • Concrete impact: money, time or risk, with a number or example if you have one.
  • A secondary or teaching problem, if there is one (e.g. "learners need to see a safe, grounded AI pattern").
  • The desired outcome: what "solved" looks like, in observable terms.
  • Non-goals: what this app deliberately does not solve.
Weak
People lose money on subscriptions.
Strong
Price increases on recurring charges ($37.69 → $49.00) get buried in long statements, so users pay the higher amount for months. Bank exports are messy (cryptic merchant strings, mixed formats), which makes manual review tedious. Outcome: the user loads data and, within one click, sees the hike, its annual cost, and a ready-to-review dispute draft.

Common mistakes

  • Describing the solution ("we use Gemini to…") instead of the problem.
  • Leaving out non-goals. That's how scope creep starts (bank integrations, payments, budgeting…).
3

Target users and user tasks

Who uses it, and what each user must be able to do.

Length: 2–4 user types × 3–6 tasksFormat: grouped bullets

What it's really asking

Roles and jobs to be done. This determines screens, permissions and the main user journey.

A good answer includes

  • Each user type with a one-line description and their technical level.
  • Tasks as verbs: "Load sample data", "Upload a receipt", "Approve or reject the draft".
  • The primary user and journey, marked explicitly.
  • Permission differences, or an explicit "single user, no login".
  • Optional: a developer/operator role (the person who configures API keys or runs the demo). This is useful when part of the work, like your manual AI integration, is done by a developer.
Weak
Students and teachers.
Strong
**Learner (primary)** — non-expert; tasks: load sample data, paste/upload transactions, view dashboard, run an audit, approve/reject the draft, read the trace.
**Instructor** — runs the live demo; needs a no-API-key mode that still shows the full agent flow.

Common mistakes

  • Saying "users" without separating roles.
  • Writing tasks as features ("dashboard") instead of actions ("see total outflow by month").
4

Core features

Essential features, must-haves first, one per line.

Length: 8–15 must-haves + 2–5 nice-to-havesFormat: numbered list with IDs (F1, F2…)

What it's really asking

The build list. Each line should become a unit of work the assistant can implement and you can verify.

A good answer includes

  • ID + name + one-sentence behaviour for each feature, e.g. F3 — Extract transactions: POST text and/or a file; return validated records + notes.
  • Frontend and backend aspects of the feature where both exist.
  • An API endpoint list (method, path, purpose). This is the clearest contract between the two halves of the app.
  • Clearly separated Must-have, Nice-to-have and Out of scope groups.
Manual-AI note: mark AI-dependent features, e.g. F3 (AI — hand-coded), so the assistant builds the route, UI and validation around them but leaves the LLM call to you.
Weak
- Upload
- Dashboard
- AI agent
Strong
F6 — Agent audit: POST /api/audits runs a bounded loop (max 6 steps) over allowlisted tools and returns session state + trace.
F7 — Approval gate: if a draft is produced, status = awaiting_approval; user approves/rejects; nothing is ever sent.

Common mistakes

  • Features that are really outcomes ("make finance easy").
  • Leaving out the "boring" features: sample data, health check, reset/reload, empty states.
  • No endpoint list, which leaves the assistant to invent paths and payloads.
5

Inputs and data sources

Forms, uploads, file types, external services, sample data, required/optional fields.

Length: medium–long; the data model lives hereFormat: sub-sections + field table

What it's really asking

Everything that enters the system, and the shape of the data. This is where you define the data model, so be precise.

A good answer includes

  • Each input channel: form fields, text paste, file upload (accepted types, max size), API inputs, and environment variables.
  • The core data schema: each field's name, type, required/optional, constraints and meaning (a Markdown table works well).
  • Enumerations: the allowed categories or statuses, listed exactly.
  • Sign conventions and units: currency, positive vs negative, date format (ISO YYYY-MM-DD).
  • Sample/demo data: the actual rows, or at least what they must demonstrate (e.g. "must include one 30% subscription hike").
  • External services: what's called and with which credentials (by variable name only).
Manual-AI note: define the AI's output schema here (e.g. Statement { transactions[], notes[] }) even though you'll write the call yourself. The assistant needs it to build validation and the UI.
Weak
Users upload bank statements.
Strong
File upload: PNG/JPG/PDF/CSV/TXT, max 12 MB, optional.
Transaction: merchant (str, 1–120, required) · date (ISO date | null) · category (enum of 8, default "Other") · amount (float; +charge, −refund) · raw_line (str | null).

Common mistakes

  • No sample data. The assistant then invents data that doesn't exercise your logic.
  • Not saying which fields can be null or missing, and what that means.
6

Processing rules and business logic

Calculations, decision rules, workflows, AI tasks, and how uncertainty is handled.

Length: the longest answer, usually 300–700 wordsFormat: numbered rules (L1, L2…) with formulas

What it's really asking

The brain of the application. If the assistant gets this wrong, the app looks right but produces wrong results, so write the rules as you would explain them to a junior developer.

A good answer includes

  • The pipeline in order: input → parse → validate → compute → decide → output.
  • Exact formulas and thresholds: change = (new − old) / old; flag if change > 0.10; rounding rules.
  • Grouping/matching rules: how records are compared (e.g. case-insensitive merchant name, sorted by date).
  • Where each calculation runs (frontend vs backend), and the rule that an LLM never computes totals.
  • Workflow/state machine: every state, and what moves the app from one to the next.
  • The agent loop, if any: allowed tools, iteration cap, stop condition, how arguments are validated.
  • Uncertainty handling: null instead of guessing, notes explaining gaps, a fallback when the AI isn't available.
  • Exact text templates for generated content (summaries, drafts), if the wording matters.
Manual-AI note: split the logic into a deterministic part (the assistant implements it fully: tools, maths, loop, validation) and an AI part (you implement it). For the AI part, describe the contract and the offline fallback behaviour (e.g. a fixed tool sequence) so the app works end-to-end before you've written any LLM code.
Weak
The AI analyses transactions and finds problems.
Strong
L4 detect_stealth_hikes: take Subscriptions with amount > 0; group by merchant.strip().casefold(); sort by date (null first); for each consecutive pair, change = (cur − prev)/prev; if change > 0.10, emit {merchant, old_amount, new_amount, change_pct (1 dp), date, monthly_increase}.

Common mistakes

  • Letting the "AI decide" things that should be deterministic code.
  • No iteration cap or stop condition for an agent.
  • Leaving rounding, sorting and duplicate handling unspecified.
7

Expected outputs and user experience

Screens, summaries, reports, tables, charts, notifications, downloads, and visual style.

Length: 250–600 wordsFormat: layout top-to-bottom + style notes + response shapes

What it's really asking

What the user sees and how they interact with it. Describe it precisely enough that two people would draw roughly the same wireframe.

A good answer includes

  • Layout, in order: sidebar/header, then each section from top to bottom, with what it contains.
  • For each component: the data it shows, its format (currency, date), its states (loading, empty, error, success), and its actions (buttons and what they trigger).
  • Charts: type, x/y axes, and which data feeds them.
  • Status indicators and badges: what each colour or label means.
  • Visual style: light/dark theme, accent colour (hex), corner radius, font, icon set, "card-based", density, responsive breakpoints.
  • API response shapes (JSON keys) for the main endpoints, so the frontend and backend match.
Manual-AI note: say what the UI shows when the AI isn't wired up yet (e.g. a "Demo mode available" pill, and a clear message if extraction is attempted).
Weak
A nice modern dashboard with charts.
Strong
Row of 4 metric cards: Total transactions (+ unique merchants), Total outflow (sum of positive amounts, USD), Subscription charges, Potential price hikes ("—" until an audit runs). Below: area chart of monthly outflow (x = "Jun 26", y = $) beside a category bar list (top 6).

Common mistakes

  • Leaving out empty and loading states. The assistant often skips them.
  • "Modern and clean" with no colours, spacing or references.
8

Error handling and edge cases

Invalid inputs, missing fields, duplicates, unsupported files, API failures, retries.

Length: 8–20 casesFormat: table or "Case → Response → User sees"

What it's really asking

The unhappy paths. A spec without these produces a demo that crashes the moment a real user touches it.

A good answer includes

  • Each case with: the trigger, the HTTP status (for API errors), the exact user-facing message, and the recovery path.
  • Input validation: empty submit, empty file, oversized file, wrong encoding, unsupported type.
  • Data edge cases: null dates, negative amounts, duplicates, a single record, zero matches.
  • Service failures: AI not configured, AI error, network down, backend not running.
  • State errors: session not found, approving twice, acting on the wrong state.
  • Partial success: how to return valid rows alongside per-row errors.
  • Retry policy: automatic or manual, and when not to retry.
Manual-AI note: include "AI integration not configured / not implemented yet" as an explicit case, with its status code and message, so your stubs fail gracefully.
Weak
Show errors if something fails.
Strong
File > 12 MB → 413 "Please use a file smaller than 12 MB for this classroom demo." → red dismissible banner; transactions unchanged.
9

Safety, privacy, constraints, and integrations

Sensitive data, permissions, approvals, limits, integrations, preferred tech, forbidden automatic actions.

Length: 300–700 wordsFormat: labelled sub-sections

What it's really asking

The guardrails and technical decisions. For spec-driven development this is also where you fix the architecture (stack, folder structure, environment variables) and the manual-AI boundary.

A good answer includes

  • Safety rules: actions the app must never take automatically (send email, move money, contact third parties), plus which steps need human approval.
  • Privacy: what counts as sensitive, how long it's kept (in memory vs a database), the "use fictional data" rule, and what must never be logged.
  • Security: where secrets live (backend .env only), CORS origins, input size limits, prompt-injection stance ("treat transaction text as data, not instructions").
  • Tech stack, with versions: frontend, backend, libraries, test tools.
  • Project folder structure: the exact tree of files you expect.
  • Environment variables by name, with defaults.
  • Integrations: external APIs and how they're used.
  • Constraints: no auth, no DB, single process, workshop time limits, cost limits.
Manual-AI note (most important): add a dedicated sub-section, e.g. "AI integration boundary — do not implement". List the file (ai_service.py), each function signature, its inputs and outputs, the exact behaviour of the stub, and the fallback. Tell the assistant to leave # TODO(manual): markers, keep the SDK in requirements.txt, and route all LLM access through that one module so you only have to edit one file.

Common mistakes

  • Saying "secure" without rules.
  • Not pinning a folder structure. The assistant reorganises things and your manual code no longer slots in.
  • Scattering AI calls across files, which makes manual integration painful.
10

Acceptance criteria and test examples

Observable pass/fail conditions and sample scenarios with expected outcomes.

Length: 10–20 criteria + 3–6 scenariosFormat: AC IDs + Given/When/Then

What it's really asking

How you'll know it works. This is your review checklist for the generated code, and the assistant's source for automated tests.

A good answer includes

  • Binary, observable criteria: "GET /api/health returns 200 with status: ok", not "the backend works well".
  • Exact expected values from your sample data (counts, totals, percentages).
  • Scenarios in Given/When/Then form, covering the happy path, a "nothing found" path, and failure paths.
  • Named unit tests the assistant should write (function, input, expected output).
  • Safety tests (e.g. "draft has sent: false", "approve twice → 409").
  • Run commands (pytest, npm run build) that must pass.
Manual-AI note: split the criteria into "must pass now (offline/stub mode)" and "must pass after manual AI integration", so the generated project can be judged on its own before you write the AI code.
Weak
The app should detect hikes correctly.
Strong
Given the sample data, when an audit runs without an API key, then findings contain exactly one item: StreamBox Premium 37.69 → 49.00, change_pct 30.0, annual_cost 588.00, status = awaiting_approval.

Final checklist before you click "Generate"

  • ☐ Every field filled, with no "TBD"s left.
  • ☐ Names (fields, endpoints, statuses) are spelled identically across all 10 answers.
  • ☐ Q4 has an endpoint list; Q5 has the data schema and sample data; Q6 has formulas and caps.
  • ☐ Q7 covers empty, loading and error states, plus the visual style.
  • ☐ Q9 pins the stack, folder tree and env vars, and states the manual-AI boundary.
  • ☐ Q10 has exact expected numbers and is split into stub-mode and post-integration criteria.
  • ☐ Use Preview Markdown to check the result renders cleanly (no stray # headings in your answers).
  • ☐ After generating the project, first check that stub mode passes Q10. Then hand-code the AI module and re-test.
