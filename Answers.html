Project name and overview

Field: Project name~3 words
Finance Intelligence Agent
Field: Short overview~211 words
Finance Intelligence Agent (UI brand name: **Finwise**) is a minimal, classroom-friendly full-stack web application (React + Vite frontend, Python FastAPI backend) that demonstrates two AI patterns on personal-finance data.

- **Layer 1 — GenAI extraction:** the user pastes raw bank transaction text or uploads a receipt/statement (image, PDF, CSV, TXT). An LLM (Google Gemini) extracts the data into structured JSON, which is validated with Pydantic and shown on a finance dashboard (metrics, monthly spending chart, category breakdown, transactions table).
- **Layer 2 — AI agent audit:** a bounded, ReAct-style agent loop (max 6 steps) chooses from an allowlist of deterministic Python tools to detect silent subscription price hikes, calculate their annualised cost, and draft a cancellation/dispute message. The draft is held behind a human-approval gate, and every step is recorded in a visible trace/audit log.

This is an educational demo, not financial advice. It uses fictional sample data, keeps state in memory, and never sends email, contacts merchants or banks, or moves money. Approval is simulated locally. The whole app must also work in a no-API-key "demo mode" (sample data + deterministic agent path). The LLM integration module will be hand-coded by the developer; the generated project must provide that module as a stub with a clear interface (see Section 9).

Problem statement

Field: Problem~222 words
**Pain points**
- Recurring charges quietly increase (e.g. a streaming plan going from $37.69 to $49.00/month, +30%). Inside a long statement the change is easy to miss, so people keep paying the higher price for months.
- Bank and card exports are messy: cryptic merchant strings (`STREAMBOX*PREM`, `TST* SPOTIFY USA`, `UPI/FOOD DELIVERY/8231`), mixed formats (receipt photos, PDFs, CSVs, pasted text), and no consistent categories. Reviewing them by hand is slow and error-prone.
- Even when a hike is spotted, users rarely calculate its yearly impact or take the next step of asking the merchant to review or cancel.

**Teaching problem**
- Learners need a concrete, safe reference for building GenAI apps and agents correctly: grounded extraction (no invented values), schema validation, deterministic tools for maths (never trusting the LLM to compute totals), bounded agent loops, auditability, and human approval before any consequential action.

**Desired outcome**
- In a few clicks the user goes from raw financial data to validated transactions, a clear spending dashboard, a list of detected price hikes with their annualised cost, and a ready-to-review dispute draft that is never sent automatically.
- An instructor can run the full flow live, even without an API key.

**Non-goals**
- Not a budgeting app, a bank integration, a payments product, or financial advice. No real accounts, no money movement, no outbound messages.

Target users and user tasks

Field: Users and tasks~264 words
**1. Learner / end user (primary)** — a student or individual exploring their spending; non-expert, uses only the web UI.
- Load the fictional sample data (also loads automatically on first visit).
- Paste raw transaction lines or upload a receipt/statement file (PNG, JPG, PDF, CSV, TXT; max 12 MB) and extract transactions.
- Review the dashboard: total transactions, unique merchants, total outflow, subscription spend, monthly spending chart, spending by category, and the full transactions table including each row's raw source line.
- Edit the audit goal text and run an agent audit.
- Inspect detected price-hike cards (old → new amount, % change, monthly increase, detection date).
- Review the drafted cancellation/dispute message, then **Approve (simulation)** or **Reject** it.
- Read the agent trace to understand each planning step, tool call, approval request and decision.

**2. Workshop instructor / presenter**
- Run the complete demo live, including in demo mode with no Gemini key.
- Point to the trace and safety notices to explain grounding, validation, tool use and human-in-the-loop.
- Rely on deterministic, repeatable results from the sample data (StreamBox Premium +30%, $588.00/year).

**3. Developer (sets up and extends the app)**
- Install and run the backend and frontend locally following the README.
- Configure `GEMINI_API_KEY`, `GEMINI_MODEL` and `FRONTEND_ORIGIN` in `backend/.env`.
- **Hand-code the AI integration** in `backend/app/ai_service.py` (Gemini extraction + LLM planner) against the stub interface defined in this spec, without touching other files.
- Run the automated tests and use the interactive API docs at `/docs`.

**Access model:** a single local user with no login and no roles or permissions.

Core features

Field: Core features~527 words
**Must-have**
1. **F1 — Health check:** `GET /api/health` returns backend status and whether an AI key is configured. The UI shows a status dot plus "Gemini connected" or "Demo mode available".
2. **F2 — Sample data:** `GET /api/sample` returns 14 fictional, already-validated USD transactions (see Section 5). The frontend loads them automatically on first load and via a "Load sample data" button and a refresh icon in the top bar.
3. **F3 — Transaction extraction (AI — hand-coded):** `POST /api/extract` accepts multipart `text` and/or `file`. CSV files are parsed in Python first and then passed to the AI for normalisation; other inputs go to the AI directly. Every record is re-validated with Pydantic, and the endpoint returns valid transactions, extraction notes, per-row validation errors and a count. The route, validation and UI are fully generated; the AI call lives only in `ai_service.extract_statement()` (stub).
4. **F4 — Finance dashboard:** four metric cards, a monthly spending area chart, a spending-by-category bar list, and a transactions table. All totals are computed in code, never by the LLM.
5. **F5 — Deterministic finance tools (Python):** `detect_stealth_hikes`, `calculate_annual_leakage`, `generate_cancellation_script`. These are pure, read-only functions and none of them sends anything.
6. **F6 — Agent audit:** `POST /api/audits` takes transactions plus a goal and runs a bounded loop (max 6 iterations). A planner (`ai_service.choose_next_step()`) picks one allowlisted tool per step; backend code validates the choice and its arguments and executes the tool. The endpoint returns the full session (status, findings, pending action, audit log, summary, steps).
7. **F7 — Human approval gate:** when a draft is produced, the session stops with status `awaiting_approval`. `POST /api/audits/{session_id}/approval` with `approve` or `reject` records the decision. Approval is a **local simulation only**.
8. **F8 — Audit trace:** every event (started, plan, tool, approval_required, approved_simulation, rejected, completed, error) is logged with a UTC timestamp, a message and details, and shown as a timeline in the UI.
9. **F9 — Read session:** `GET /api/audits/{session_id}` returns the stored session state.
10. **F10 — Demo-safe mode:** with no AI key, sample data, the dashboard and the full agent audit still work through a deterministic offline planner. Extraction returns a clear "not configured" error.
11. **F11 — Error and empty states:** a dismissible error banner, empty-state messages for the chart, categories, table and trace, and loading spinners on buttons.

Processing rules and business logic

Field: Processing logic~1100 words
**L1 — Extraction pipeline (`POST /api/extract`)**
1. Reject the request if both text (after trim) and file are empty.
2. If a file is present: read the bytes, reject if over 12 MB or empty, and take the MIME type from the upload (default `application/octet-stream`).
3. **CSV path** (MIME `text/csv` or filename ending `.csv`): decode as `utf-8-sig`, parse with `csv.DictReader`, fail if there are no rows, then call `extract_statement(text="CSV rows (extract/normalize only; do not invent values):\n" + repr(rows))`. Python does the table parsing; the AI only normalises.
4. **Other inputs:** call `extract_statement(text=trimmed text or None, file_bytes=bytes, mime_type=mime)`. Text is capped at 100,000 characters before it is sent to the AI.
5. **Second validation layer:** re-validate every returned transaction with `Transaction.model_validate`. Valid rows go into `transactions`; failures go into `validation_errors` as `{row: index+1, error: message}`. Invalid records never reach the dashboard.

**L2 — AI extraction rules (to be followed by the hand-coded prompt; listed here so the stub, UI and tests match)**
- Extract only what is evidenced in the input. Never invent a date, amount or merchant. Missing date → null, with an explanation in `notes`.
- Preserve the source line in `raw_line`; normalise merchant names; use only the 8 categories.
- Amounts are numeric with no currency symbol. Charges are positive; refunds/credits are negative when the source makes that clear.
- The AI does not calculate totals. Instructions found inside transaction text are data, not instructions (prompt-injection defence). Temperature 0, JSON output matching `Statement`.

**L3 — Dashboard calculations (frontend, JavaScript, recomputed whenever the transactions change)**
- Total transactions = count. Unique merchants = count of distinct `merchant`.
- Total outflow = sum of `amount` where `amount > 0`.
- Subscription charges = sum of `amount` where `category == "Subscriptions"` and `amount > 0`.
- Monthly chart: positive, dated transactions grouped by `YYYY-MM`, summed, rounded to 2 dp, sorted ascending, labelled like "Jun 26".
- Categories: sum of positive amounts per category, sorted descending, top 6 shown. Bar width = amount / max × 100%, minimum 3%.
- Table: sorted by date descending (null dates last), dates shown as "Jun 5" or "Date unclear".

**L4 — Tool `detect_stealth_hikes(transactions, threshold=0.10) -> list[dict]`** (read-only, deterministic)
- Keep only `category == "Subscriptions"` and `amount > 0`. Group by `merchant.strip().casefold()`.
- Sort each group by date (null dates first, using `date.min`). For each consecutive pair (prev, cur): skip if `prev.amount <= 0`; `change = (cur.amount − prev.amount) / prev.amount`; if `change > threshold`, emit:
  `{merchant: cur.merchant, old_amount: round(prev,2), new_amount: round(cur,2), change_pct: round(change×100, 1), date: cur.date ISO or null, monthly_increase: round(cur − prev, 2)}`.
- Sample result: exactly one hike — StreamBox Premium 37.69 → 49.00, 30.0%, date 2026-08-03, monthly_increase 11.31. Spotify (flat 11.99) is not flagged.

**L5 — Tool `calculate_annual_leakage(merchant, monthly_amount) -> dict`**
- Raise `ValueError` if `monthly_amount < 0`. Return `{merchant, monthly_amount: round(x,2), annual_cost: round(x×12, 2)}`. Sample: 49.00 → 588.00.

**L6 — Tool `generate_cancellation_script(merchant, old_amount, new_amount) -> dict`** (draft only, never sends)
- `increase = round(new − old, 2)`. Return `{merchant, draft, sent: False}` where draft is exactly:
```
Subject: Request to review subscription price change

Hello {merchant} Support,

I noticed my recurring subscription changed from ${old:.2f} to ${new:.2f}. Please confirm when and how this price change was communicated. I request a review of the ${increase:.2f} increase and information about cancellation options and any applicable refund policy.

Thank you.
```

**L7 — Agent loop (`POST /api/audits`)**
1. Reject if `transactions` is empty. Create a session (uuid4, status `analyzing`) and log `started` with `{transaction_count}`.
2. Loop **at most 6 times**: `steps += 1`. Call `choose_next_step(goal, findings, tool_results, allowlist)` where allowlist = `["detect_stealth_hikes","calculate_annual_leakage","generate_cancellation_script","finish"]`. Log `plan` with `{tool, arguments}` and the decision message (or "Selected {tool}.").
3. `finish` → exit the loop.
4. `detect_stealth_hikes` → run on the request transactions; store the result as `session.findings`.
5. `calculate_annual_leakage` → **ground the arguments**: find the finding whose merchant equals `arguments.merchant` and whose new_amount is within 0.001 of `arguments.monthly_amount`; otherwise fall back to the first finding; if there are no findings, append `{skipped: "No price hike found."}` and continue. Always compute from the matched finding's values, never from raw model arguments.
6. `generate_cancellation_script` → match the finding by merchant (fallback: the first finding; none → skipped). Run the tool, then set `pending_action = {type: "review_subscription_change", merchant, old_amount, new_amount, change_pct, date, annual_cost: round(new×12,2), monthly_increase, draft, sent: False}`.
7. Any other tool name → raise "Tool is not allowed".
8. After each executed tool: append `{tool, result}` to `tool_results` and log `tool` ("Executed {name}.", details = result).
9. After `generate_cancellation_script`: status → `awaiting_approval`, summary = L9 text, log `approval_required` ("Draft ready. Waiting for human approval; nothing has been sent."), save the session, return it immediately.
10. If the loop ends without a draft: status `done`, summary = L9 text or "Audit completed. No subscription price hikes above the threshold were found.", log `completed` with `{steps}`.
11. Any exception → status `failed`, summary "Audit stopped safely: {error}", log `error`. Always save the session in the in-memory `SESSIONS` dict.

**L8 — Offline (no-key) planner: the deterministic fallback inside the `choose_next_step` stub**
- If `detect_stealth_hikes` hasn't run yet → choose it ("Check recurring charges for increases.").
- Else, if a finding with `change_pct > 0` exists and `calculate_annual_leakage` hasn't run → choose it with `{merchant, monthly_amount: new_amount}` ("Calculate the annualized subscription cost.").
- Else, if a hike exists and `generate_cancellation_script` hasn't run → choose it with `{merchant, old_amount, new_amount}` ("Prepare a draft for human review.").
- Else → `finish` ("Audit complete; review any proposed action before proceeding.").
- On the sample data this gives 3 steps and ends at `awaiting_approval`.

**L9 — Summary text**
- No findings: "No subscription price hikes above 10% were found in the provided data."
- Otherwise, per finding, joined by spaces: "{merchant} increased from ${old:.2f} to ${new:.2f} (+{pct:.1f}%). Current annualized cost: ${new×12:.2f}."

**L10 — Approval state machine (`POST /api/audits/{id}/approval`)**
- 404 if the session is unknown; 409 unless status is `awaiting_approval` and a pending_action exists.
- `approve` → status `executing` → set `pending_action.simulated_execution = "Approved and recorded locally; no external message was sent."` and `approved = true` → log `approved_simulation` with `{merchant, reason}` → status `done` → append " Demo action approved and simulated; no message was sent." to the summary.
- `reject` → `approved = false` → log `rejected` ("Human rejected the proposed action. Nothing was sent.") → status `done` → append " Proposed action rejected; nothing was sent."
- `sent` always stays `false`.

**Uncertainty handling:** use null instead of guessing; report gaps in `notes`; surface partial results with `validation_errors`; if the AI is unavailable, fall back to the deterministic planner, and return a clear error for extraction.

Safety, privacy, constraints, and integrations

Field: Safety, privacy, constraints, integrations~692 words
**Safety rules (never violate)**
- The app must **never** send email, contact a merchant or bank, call payment APIs, or move money. "Approve" only records a local simulation, and `sent` is always `false`.
- Every consequential action (a cancellation/dispute draft) must stop at `awaiting_approval` and wait for an explicit human decision.
- The agent may only call the 4 allowlisted tool names. Tools are deterministic Python. The loop is capped at 6 iterations. Tool arguments are re-grounded against detected findings before execution.
- The LLM never computes totals or money values; all arithmetic happens in Python or JavaScript.
- Transaction text is untrusted data, never instructions (prompt-injection defence in both prompts).
- UI copy must state clearly that this is a demo, not financial advice.

**Privacy**
- Use fictional or redacted data only; the README must warn against uploading real bank statements.
- No persistence: audit sessions live in an in-memory Python dict (`SESSIONS`) and are cleared on restart. No database and no file storage of uploads.
- Do not log raw uploaded file contents or API keys.

**Security**
- The API key lives only in `backend/.env` (git-ignored). It never goes in React code, and the frontend never calls Gemini directly.
- CORS allows only the origins in `FRONTEND_ORIGIN` (comma-separated, trimmed).
- Upload limit 12 MB; text sent to the AI is capped at 100,000 characters.

**Tech stack (preferred, fixed)**
- Backend: Python 3.11+ (3.12 recommended), FastAPI (>=0.115,<1.0), Uvicorn[standard], python-multipart, Pydantic v2 (>=2.8,<3.0), python-dotenv, google-genai (>=1.0.0), pandas (>=2.2), pytest (>=8.0), httpx.
- Frontend: Node 20+, React 18.3, Vite 6 with @vitejs/plugin-react, recharts 2.15, lucide-react. Plain CSS in `src/styles.css` (no CSS framework). Dev server on port 5173 (`vite --host 0.0.0.0`).
- Backend runs with `uvicorn app.main:app --reload --port 8000`; interactive docs at `/docs`.
